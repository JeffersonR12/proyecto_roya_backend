1. IDENTIDAD DEL PROYECTO
================================================================

Nombre visible: Roya
Componente principal de la app autenticada: RoyaGuard
Proposito: registrar inspecciones de campo de Roya Amarilla en hojas de cultivo.
El tecnico captura o sube una imagen, el sistema estima una afectacion y guarda la inspeccion en la bitacora del usuario.
El administrador ve las inspecciones de todos los usuarios. El tecnico solo ve las suyas.

La "IA" actual es una inferencia LOCAL SIMULADA en el navegador.
No hay modelo de machine learning, ni API externa de vision, ni procesamiento de imagen en el servidor.
La enfermedad guardada siempre es el texto "Roya Amarilla".
La afectacion sale de una muestra aleatoria fija en el cliente.

4. REQUERIMIENTOS FUNCIONALES IMPLEMENTADOS
================================================================

RF-01. Acceso de invitados y de usuarios autenticados
- Invitado que abre una ruta con middleware auth es redirigido a la ruta nombrada login (/login).
- Usuario autenticado que abre una ruta con middleware guest es redirigido a la ruta nombrada home (/).
- Configurado en bootstrap/app.php: redirectGuestsTo login, redirectUsersTo home.

RF-02. Pantalla de inicio de sesion
- GET /login, nombre login, solo invitados. Vista page=login.
- Campos: correo, contraseña, casilla Recordarme, enlace a recuperar contraseña, enlace a crear cuenta.
- Botones "Usar admin" y "Usar tecnico" solo aparecen si urls.demoLogin es true (APP_ENV=local). Solo rellenan el formulario. No envian la peticion solos.
- Credenciales que rellenan:
  admin: admin@gmail.com / password / remember_me true
  tecnico: tecnico@gmail.com / password / remember_me true
- Esas cuentas las crea database/seeders/DatabaseSeeder.php (updateOrCreate). No asumas que existen si no se ejecuto el seeder.
- El correo se normaliza en cliente y servidor: trim + minusculas.
- Validacion de formato Gmail en cliente (resources/js/lib/auth.js) y en servidor (LoginRequest + AuthRules).
- POST /login espera JSON cuando el cliente es axios (Accept application/json).
- Respuesta correcta JSON: success true, message "Sesion iniciada correctamente.", redirect a route('home').
- El cliente redirige con window.location.href a response.data.redirect o a urls.home.
- Si no es JSON, el servidor hace redirect intended a home.
- Error de credenciales: mensaje "Las credenciales no son validas." en el campo credentials.
- Errores de validacion se muestran con firstError (resources/js/components/Field.jsx).
- Se puede mostrar u ocultar la contraseña.
- Checkbox remember_me se envia como booleano.

RF-03. Reglas de autenticacion
- Archivo: app/Support/AuthRules.php
- Correo obligatorio, string, max 255, regex: /^[a-zA-Z0-9._%+-]+@gmail\.com$/
- Solo se aceptan correos @gmail.com. No se aceptan otros dominios.
- Contraseña de login: obligatoria, string. No se reaplica la regla de 8 caracteres en el login.
- Recordarme: a veces, booleano. Duracion del remember: 43200 minutos (30 dias), via Auth::guard('web')->setRememberDuration.
- Intentos fallidos: maximo 5 por minuto, por correo e IP juntos. Clave manual: "login-attempt:{email}|{ip}". El middleware throttle:login usa "{email}|{ip}". Decaimiento del limitador manual: 60 segundos.
- Al superar el limite: "Demasiados intentos. Espera {segundos} segundos e intentalo de nuevo."
- POST /login tambien lleva middleware throttle:login.
- throttle:login esta definido en AppServiceProvider: 5 intentos por minuto, por correo e IP.
- Si el middleware de Laravel responde 429, bootstrap/app.php devuelve JSON cuando la peticion espera JSON:
  message y errors.credentials = "Demasiados intentos. Espera un momento e intentalo de nuevo."
- Login exitoso limpia el rate limiter, regenera la sesion y guarda last_login_at = now().
- En produccion (app()->isProduction()), el login aborta 403 si la peticion no es HTTPS, con texto "El inicio de sesion solo se permite por HTTPS." En local este bloque no aplica.

RF-04. Registro de cuenta
- GET /register, nombre register, solo invitados. Vista page=register.
- POST /register, solo invitados.
- Campos: name obligatorio max 255; email obligatorio unico en users, formato Gmail, max 255; phone opcional max 30; organization opcional max 255; password obligatoria, confirmada, minimo 8, con letras, mayusculas, minusculas y un numero; terms debe estar aceptado.
- El formulario publico no pide rol. Aunque el cliente envie role=administrador, el servidor guarda role=tecnico. El administrador solo se crea en DatabaseSeeder.
- terms no se persiste. User::create recibe el payload seguro excepto terms y fuerza role tecnico.
- Mensajes de validacion en español, definidos en RegisterRequest.
- Al crear la cuenta: Auth::login, regenerar sesion, last_login_at = now().
- Respuesta JSON 201: success true, message "Cuenta creada correctamente.", redirect a home.
- Si no es JSON: redirect a home.
- Tras el registro el usuario entra directo a la app. No hay verificacion de correo.

RF-05. Recuperacion de contraseña
- GET /forgot-password, nombre password.request, solo invitados. Vista page=forgot.
- POST /forgot-password valida email obligatorio con el mismo regex de Gmail.
- Respuesta JSON siempre con el mismo texto, exista o no el correo:
  success true, message "Si el correo existe, te enviaremos instrucciones para restablecer la contraseña."
- Si el correo existe, crea un token en password_reset_tokens y envia App\Notifications\ResetPasswordNotification.
- El correo usa el mailer de .env. En local (MAIL_MAILER=log) el mensaje queda en storage/logs/laravel.log.
- Solo si APP_ENV=local y el correo existe, la respuesta incluye reset_url para abrir el enlace sin leer el log. En testing y production esa clave no se envia.
- GET /reset-password/{token}, nombre password.reset, solo invitados. Vista page=reset. El correo llega por query email.
- POST /reset-password, nombre password.update. Exige token, gmail y contraseña con las mismas reglas del registro.
- Si el token sirve: actualiza password, regenera remember_token y responde redirect a login.
- Si el token no sirve: "El enlace no es valido o ya expiro. Solicita uno nuevo."

RF-06. Cierre de sesion
- POST /logout, nombre logout, solo autenticados. El cliente llama /logout.
- Auth::logout, invalida la sesion y regenera el token CSRF.
- JSON: success true, redirect a route('login').
- Si no es JSON: redirect a login.
- Sidebar llama axios.post(logoutUrl) y luego window.location.href = '/login'.

RF-07. Pantalla principal autenticada
- GET /, nombre home, solo autenticados. AnalysisController@index.
- Devuelve view app con page=app, listing (pagina, recientes, actividad, stats) y authUser.
- RoyaGuard muestra dos modos internos, no son rutas distintas:
  mobile = inspeccion de campo (Scanner)
  desktop = dashboard + historial
- Rol administrador abre por defecto en desktop.
- Cualquier otro rol, incluido tecnico, abre por defecto en mobile.
- Sidebar: Campo (mobile), Dashboard (desktop), Salir, y tarjeta "Nueva captura" que fuerza modo mobile.
- En viewport pequeño el sidebar es un menu deslizable con fondo oscuro. En md o mayor queda fijo.
- Topbar: buscador, iniciales del nombre, nombre y etiqueta de rol. No hay campana de notificaciones.
- Etiqueta de rol: administrador -> "Administrador"; cualquier otro -> "Tecnico de campo".

RF-08. Visibilidad de inspecciones por rol
- AnalysisController::visibleAnalyses:
  si role !== 'administrador', filtra analyses.user_id = usuario actual.
  si role === 'administrador', devuelve todas.
- Orden: latest() (created_at descendente) con relacion user cargada.
- User::isAdmin() existe y compara role === 'administrador', pero el controlador compara el string directamente. Conserva ambos comportamientos.

RF-09. Inspeccion de campo (Scanner)
- Componente: resources/js/components/Scanner.jsx
- Dos fuentes, controladas en el cliente: Camara y Subir archivo.
- Camara: getUserMedia con video facingMode ideal environment, sin audio.
- Si el navegador no tiene mediaDevices, mensaje para usar la pestaña de subida.
- Si el permiso falla, mensaje para revisar permisos o usar subida.
- Botones: Activar camara y Tomar fotografia. Tomar fotografia permanece deshabilitado hasta que la camara este lista.
- La foto se dibuja en un canvas oculto y se convierte a JPEG data URL con calidad 0.82.
- Subida: input file accept image/jpeg, image/png, image/webp, y arrastrar y soltar.
- El cliente solo comprueba que file.type empiece por "image/". No impone 5 MB en el navegador.
- Campo de ubicacion libre, placeholder "Lote, vereda o finca". Si queda vacio se envia null.
- Boton "Escanear con IA" deshabilitado si no hay imagen o si ya se esta guardando.
- Al escanear el cliente solo envia image_base64 y location. No envia disease_detected ni confidence.

- El resultado visual usa response.estimate y solo aparece si el POST responde 201.
- Exito: "Estimacion simulada guardada: {severity}% de afectacion." Luego se recarga el listado.
- Fallo: muestra el error de image_base64 o location, o "No se pudo guardar la inspeccion." No muestra diagnostico.
- La pantalla dice que la estimacion es simulada.

RF-10. Clasificacion de riesgo y recomendaciones
- Una sola escala, en App\Support\Risk.php y resources/js/lib/risk.js.
- confidence de 0 a 1:
  mayor que 0.3 -> critical, etiqueta CRITICO, recomendacion "Cuarentena inmediata y aplicacion de fungicida sistemico"
  mayor o igual a 0.1 y menor o igual a 0.3 -> medium, etiqueta ALERTA MEDIA, recomendacion "Reinspeccionar en 48 horas y vigilar humedad"
  menor que 0.1 -> healthy, etiqueta SANO, recomendacion "Mantener plan preventivo"
- El escaneo muestra la etiqueta y la recomendacion que devuelve el servidor en estimate.
- summarizeAnalyses cuenta total, critical (confidence > 0.3), medium (>= 0.1 y <= 0.3) y healthy (< 0.1).
- percent(value) muestra value * 100 con 1 decimal por defecto. El historial y las alertas usan 0 decimales.
- formatDateTime: dd/mm/aaaa hh:mm en hora local del navegador.

RF-11. Guardado de inspeccion en servidor

- Respuesta JSON 201: success, message "Inspeccion guardada correctamente.", analysis con user, y estimate (level, label, severity, recommendation).

8. CHECKLIST ANTES DE DAR POR TERMINADO UN CAMBIO
================================================================

- Un invitado puede abrir /login, /register y /forgot-password.
- Un invitado que abre / termina en /login.
- Un autenticado que abre /login termina en /.
- Login con correo que no sea @gmail.com muestra el error de formato y no crea sesion.
- Login incorrecto muestra "Las credenciales no son validas."
- Login correcto entra a RoyaGuard y actualiza last_login_at.
- Registro exige nombre, gmail unico, contraseña de 8 caracteres con mayusculas, minusculas y numero, y terminos. La cuenta queda como tecnico.
- Registro inicia sesion y lleva a /.
- Recuperar contraseña crea token y envia el correo si la cuenta existe. La pantalla de nueva contraseña esta en /reset-password/{token}.
- Logout vuelve a /login y la sesion deja de servir para / y /analysis.
- Tecnico solo ve sus inspecciones. Administrador ve todas.
- Administrador abre en Dashboard. Tecnico abre en Campo.
- Escanear exige imagen JPG, PNG o WEBP de hasta 5 MB. El servidor guarda el archivo, asigna Roya Amarilla y la confidence simulada, y el diagnostico solo aparece si la respuesta es 201.
- Riesgo: confidence > 0.3 critico, >= 0.1 y <= 0.3 alerta media, < 0.1 sano.
- Busqueda filtra en el servidor por enfermedad, ubicacion y nombre del tecnico.
- Historial filtra por nivel de riesgo y pagina de 12.
- Descargar reporte abre /analysis/export y escapa comas con fputcsv.
- No se rompio CSRF, el remember de 30 dias, ni el limite de 5 intentos por minuto por correo e IP.

9. ISO Y CONDICION DE SAAS
================================================================

Conclusion: el proyecto NO tiene ninguna ISO implementada y NO es un SaaS.
No hay certificacion, politica, manual, matriz de controles, evaluacion de riesgos ni declaracion de aplicabilidad.
No hay multi-tenant, planes, facturacion, aislamiento de organizaciones ni acuerdo de nivel de servicio.
Un agente no debe describir Roya como certificado, conforme o "listo para SaaS". No debe agregar controles de ISO ni arquitectura SaaS salvo que el usuario lo pida en ese momento.

Inventario por norma. Estado real en este repositorio:

ISO/IEC 27001 (sistema de gestion de seguridad de la informacion)
- NO IMPLEMENTADA.
- No existe SGSI, alcance, dueno del riesgo, tratamiento de riesgos, auditoria interna ni mejora continua.
- Lo unico cercano, y no equivale a la norma, es tecnico: hash de contraseñas, CSRF, regeneracion de sesion, limite de 5 intentos de login por correo e IP, HTTPS obligatorio solo en el login cuando APP_ENV=production, y filtro de inspecciones por rol dentro de una sola base de datos.

ISO/IEC 27002 (controles de seguridad)
- NO IMPLEMENTADA como catalogo de controles.
- No hay inventario de activos, control de accesos formal, gestion de cambios, copias de seguridad, registro de auditoria ni gestion de incidentes.
- last_login_at es la unica marca de acceso persistida. No hay log de quien creo, vio, exporto o intento borrar datos.

ISO/IEC 27017 (controles de seguridad para servicios en la nube)
- NO IMPLEMENTADA.
- La app no declara un modelo de responsabilidad compartida, ni separacion entre clientes de nube, ni configuracion de proveedor cloud.
- Corre en un solo despliegue (por defecto SQLite local, pensado para XAMPP o php artisan serve). Un administrador ve los datos de todos los usuarios.

ISO/IEC 27018 (proteccion de datos personales en nube publica)
- NO IMPLEMENTADA.
- Se guardan datos personales (nombre, correo, telefono, organizacion, imagenes de campo en base64) sin politica de privacidad, sin finalidad documentada, sin plazo de conservacion, sin derecho de acceso, rectificacion o supresion, y sin cifrado de la base.
- SESSION_ENCRYPT=false. La imagen viaja y se almacena como texto.
- La casilla "Acepto el uso de datos para inspecciones agricolas" no es un aviso de privacidad ni un contrato de encargado de tratamiento.

ISO/IEC 27701 (gestion de privacidad)
- NO IMPLEMENTADA. No hay sistema de gestion de informacion de privacidad ni roles de responsable y encargado.

ISO/IEC 25010 (calidad del producto de software)
- NO ADOPTADA. Nadie evaluo el producto contra sus caracteristicas (adecuacion funcional, rendimiento, compatibilidad, usabilidad, fiabilidad, seguridad, mantenibilidad, portabilidad).
- Hay calidad parcial de hecho (interfaz en español, validacion, roles, responsive), pero eso no es una implementacion de la norma.

ISO 9001 (gestion de la calidad)
- NO IMPLEMENTADA. No hay procesos documentados, no conformidades, acciones correctivas ni auditoria de calidad.

ISO/IEC 20000 (gestion de servicios de TI)
- NO IMPLEMENTADA. No hay catalogo de servicio, mesa de ayuda, cambios, entregas ni SLA.

ISO 22301 (continuidad del negocio)
- NO IMPLEMENTADA. No hay plan de continuidad, respaldo operativo ni recuperacion ante desastre. Perder database/database.sqlite pierde usuarios e inspecciones.

Por que tampoco es un SaaS:

- Un SaaS se entrega por internet a varios clientes, con alta centralizada, aislamiento de los datos de cada cliente y, en la practica, suscripcion.
- Roya es una aplicacion web de una sola organizacion logica: usuarios comparten la misma base y el rol administrador cruza todos los registros.
- El registro crea un usuario, no un inquilino ni una suscripcion.
- No hay cobro, planes, limites por cliente, panel de operador ni aprovisionamiento automatico.
- No hay API para que otros sistemas consuman el servicio.

Controles tecnicos que SI existen y un agente debe conservar, sin llamarlos ISO ni SaaS:

- Autenticacion por sesion, CSRF, hash de contraseña, remember de 30 dias.
- Limite de 5 intentos de login por minuto por correo e IP.
- HTTPS forzado solo en el login de produccion.
- Separacion tecnico/administrador sobre las inspecciones, dentro de la misma base.
- Validacion de correo @gmail.com, contraseña minima de 8 caracteres en el registro y aceptacion de terminos.
